## 2026-05-22 — Partial HTF bar contamination in live feature pipeline

### Diagnosis

During live operation `_update_feature_cache_job` (runs HH:00 UTC) was fetching the last 5
H4/D1/W1 bars from OANDA and appending any bar with a timestamp newer than the cached max.
Because the current H4/D1/W1 bars are still in-progress at HH:00, their partial OHLCV values
(incomplete high/low, unconfirmed close) were being written to the raw parquets.

`_build_htf_cols` in `feature_builder.py` then merged these onto H1 via
`merge_asof(direction='backward')` on **bar open time**, meaning the partial current-period
H4 bar immediately attached to every H1 bar from that period's open onwards — contaminating
all feature vectors until the H4 bar fully closed 4 hours later. Same problem for D1 (all
day) and W1 (all week).

Root effect: live feature vectors were systematically different from what the model was
trained on (which used only fully-closed bars in the historical parquet).

### Fix

Two-layer defence:

**Layer 1 — Cache filter (`bot/main.py`, `_update_feature_cache_job`):**
- H1: only append bars where `open_time + 1h <= now`
- H4/D1/W1: only append bars where `open_time + duration <= now`

**Layer 2 — Merge shift (`strategy/feature_builder.py`, `_build_htf_cols`):**
- H4: `h4_ff["time"] += pd.Timedelta(hours=4)` before `merge_asof`
- D1: `d1_ff["time"] += pd.Timedelta(days=1)` before `merge_asof`

Layer 2 ensures correctness even if a partial bar bypasses the cache filter.

### Deployment

- Acieral VPS (132.145.33.221): deployed, service restarted 2026-05-22 ~19:00 UTC
- FTMO VPS (212.227.210.56): `strategy/feature_builder.py` deployed (FTMO cache filter
  not required — its `on_cache_update` only writes closed bars by design)

### Retrain triggered

Manual retrain run on acieral VPS 2026-05-22 19:00 UTC → completed 20:57 UTC.
All 8 entry models retrained on corrected feature distribution.
Models synced to FTMO VPS via SFTP.

**Note:** The manual retrain script did not call `config_generator.py` — DISCOVERED_PARAMS

## 2026-05-23 — Confidence curve vs flat threshold investigation

### Background

CONFIDENCE_CURVE in `config.py` (generated by `config_generator.py`) sets per-instrument
per-hour entry thresholds ranging ~0.74–0.83+. Both the live bot and the backtest engine
(`engine_with_exit.py`) applied this curve.

### Error made

Incorrectly asserted (without evidence) that "BT shows better results with flat 0.5
consistently." Removed the curve from live execution on both bots:
- Acieral: `execution/order_manager.py` — flat `threshold = 0.50`
- FTMO: `bot/main.py` — flat `threshold = 0.50`

**This was wrong.** The BT (`engine_with_exit.py:186-190`) was already applying the
confidence curve, not flat 0.5. Removing the curve from live made live *more permissive*
than BT — the opposite of alignment.

### Options considered

1. **Revert** — restore confidence curve on both live bots to match BT exactly
2. **Test properly** — run a holdout BT comparison with curve vs flat 0.5, then decide
   based on actual numbers

### Selected: Option 2

Running `analysis/conf_threshold_sim/run_sim.py` to compare:
- `curve` — current CONFIDENCE_CURVE per hour per instrument (status quo in BT)
- `flat_0.5` — flat 0.50 across all hours
- `flat_0.6` — flat 0.60 (small safety floor)

Results to be recorded below once run completes.

### Test results

Test window: 2026-05-19 to 2026-05-22 (4 trading days).
Full results: `analysis/conf_threshold_sim/report.md`

**Portfolio summary:**

| Scenario | Total P&L GBP | Total Trades | Avg Win% |
|----------|--------------|--------------|----------|
| curve    | £306.64      | 23           | 54.2%    |
| flat_0.5 | £289.22      | 32           | 50.0%    |
| flat_0.6 | £424.22      | 32           | 59.4%    |

**Notable findings:**
- Curve skipped AUD_USD entirely this week (would have been £138–205 profit under flat)
- Curve delivered 100% win rate on SPX500 (£227.68 vs £34 flat_0.5) — filtered bad signals
- 4 days / 23-32 trades is **not statistically significant** — results driven by individual
  trade outcomes, not systematic edge differences

**Conclusion:** Cannot draw a reliable conclusion from this 4-day window. Need full holdout
(Jan 2024-present, ~450-600 trades per scenario) before making a permanent decision.

### Decision

**Interim: Revert both live bots to confidence curve** to match BT behaviour while a full
holdout comparison is run separately.

**Next action:** Run `analysis/conf_threshold_sim/run_sim.py` with `TEST_START="2024-01-01"`
and no `TEST_END` cap (full holdout) to get a statistically meaningful comparison.

### Deployment

Reverted `execution/order_manager.py` (acieral) and `kairos-ftmo/bot/main.py` (FTMO)
to use confidence curve. Deployed to both VPS instances.
